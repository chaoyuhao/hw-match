## 结论与限制

- 13/15 个点变快，第 13 点改善最大，约 8.07 倍。第 1、2 点分别慢了 5.78%、2.93%；这里只有单轮记录，尚不能区分稳定退化和运行波动。
- 第 13 点仍为最优的 45.78 倍；第 8、15 点约为最优的 19 倍。多数点的差距仍然很大，不能只用本地大 M 单例的 10.53 倍加速评价整个提交。
- 第 1–5 点约 11–14 μs，且前两个点没有受益，提示固定路径开销值得单独分析。缺少 shape 和线上流水线数据，不能据此断言它们一定是小矩阵，更不能认定 12 μs 全是 kernel launch 开销。
- README 说明最终分数取 15 个测试点得分均值；现有文本文档缺失具体单点计分公式，不用总耗时、平均加速比或最优耗时比估算得分和名次。

## 下一轮方向

1. **先验证更合适的 Matmul 分块。** 当前所有 shape 使用外层 32×64 tile；本地 M=8192,N=65 会调用 512 次 Matmul，其中 256 次只有一列输出。比较 64×128、128×128 等候选，同时检查核数利用率、长 K、转置和尾块。减少 API 调用次数不等于等比例提速。
2. **小规模计算单独评估简化路径。** 根据真实 B/M/N/K 和布局分派，测试减少跨核屏障、通信和 scratch 往返的路径；保持一次 launch、真实输入计算和精度要求。不能按线上测试点编号分派，也不预先指定未经测量的阈值。
3. **进一步融合 Matmul 与 Max。** 将 C 分块交给 Vector 后尽早归约，逐步减少完整 similarity 的存储生命周期和重复读写。CANN 支持 Iterate/GetTensorC 将 C 分块交到 VECIN，但这不证明该路径内部完全不经 GM workspace；必须核对实现及 profiler。参见 [GetTensorC 官方接口](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/ascendcopapi/docs/en/api/SIMD-API/advanced_api/matrix_compute/Matmul-Kernel/GetTensorC.md)。

这些是待验证的方向，不是由线上点号反推出来的确定瓶颈。保留 `72abad1` 作为已获线上 15/15 反馈的回退版本，每轮修改分别比较完整正确性和各类 shape 的性能。
