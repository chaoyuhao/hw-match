## README 对当前实现的具体提示

题目在[核心难点](../README.md#L36)和[性能要求](../README.md#L116)中明确提出四种布局、非对齐尾块、小 batch、大 M/N/K、Cube/Vector 协作、存储复用、多核均衡及 Double Buffer/Ping-Pong。这些是优化方向，不意味着每项都必须采用某一种实现。

## 核心数据流仍有三段阶段边界

当前单次 kernel 内的顺序是：

```text
所有 Matmul 任务 → 完整 similarity 写 GM
    → 全 AIV 同步
    → 所有行最大值任务 → maxima 写 GM
    → 全 AIV 同步
    → 每个输出 owner 串行补偿求和
```

当前显式 scratch 字节数为：

```text
4 * B * M * round_up(N, 16)
  + 4 * B * round_up(M, 32)
```

此外还有 Matmul 系统 workspace。一次 kernel launch 满足了平台启动次数要求，但不代表已经实现了逐块数据复用和跨阶段流水。

官方 [Matmul + Abs 直调示例](../cann-learning-hub/tutorials/ascendc_operator_development_light/03_simple_operator_practice/answer/03.05/matmul_abs.asc) 提供了 Iterate/GetTensorC 后接 Vector 处理的流程，可以作为候选数据流的参考。示例为固定 shape、FP16、有 bias、MIX 1:2，不能直接替换我们的 BF16/四布局/尾块处理。910B 上 LocalTensor 接口也不保证底层完全绕过 GM。

## 分块规则目前在四处重复

1. `kernel.asc` 的候选数组和 policy 编号范围。
2. [local/runner.asc](../local/runner.asc#L45) 的字符串到编号映射。
3. [scripts/local_baseline.py](../scripts/local_baseline.py#L174) 的候选白名单与计划校验。
4. [scripts/tile_sweep.py](../scripts/tile_sweep.py#L10) 的遍历列表和表头。

因此，当前增加一种 tile 需要同步修改选择、控制、验证和报告四层。校验应继续严格，但应检查实际执行计划的结构、约束和身份，而不是让 Python 复制一份独立的候选生成算法。

值得采用的边界是：Host 规划器产生完整的执行计划；本地 runner 能导出同一规划器产生的候选及最终选择；采样器按候选清单运行并记录实际执行计划。Device 只执行已选择的合法方案。正式调用中不进行试跑搜参，候选枚举也要有数量和 Host 开销上限。

## 各优化模块必须共同决定的事情

分块不是孤立的两个整数。一个执行方案还包含任务所有权、内部 Matmul 配置、缓冲数量、结果块格式、N 分片数、归约方式和同步参与者。

例如，增大 C 块可能减少 Matmul 调用，却挤占 UB，使双缓冲或行最大值暂存无法成立；只沿 M 分工有利于在 owner 内累计行最大值，但小 B/M、大 N 时可能任务不足。候选合法性和选择必须考虑这些耦合。

可以按三层组织后续设计：

- **问题与硬件描述**：逻辑 B/M/N/K、真实存储跨度、dtype、布局、可用核数和目标资源能力。保留现有 metadata 校验，避免重复解释 transpose。
- **计划生成与约束检查**：由规则产生分块和调度候选，排除资源不合法的组合，再用有明确假设的成本估计选择方案。外层 tile 与库内部 tiling 分别记录。
- **设备执行与验证**：少量明确的 kernel 路径消费计划；本地工具导出候选、生成输入、验证结果并关联测量。后续决策树是选择规则的一种表达方式，不要求每个分支对应一个手写 shape。

这些是架构讨论的边界，具体数据结构、文件拆分和 API 需在实现设计中确定；模块化本身不等于性能提升。

## 数值正确性与调度空间

README 要求先沿 N 取最大值，再沿 M 求和，并要求重复结果一致。它没有规定 M 维求和必须采用当前逐项串行 Kahan 顺序。

因此，固定结构的树形或向量求和可以作为候选，但 FP32 加法重排会改变误差，必须通过 FP64 golden、强抵消、近零结果和重复一致性检查。现有串行补偿求和是可用的参照，不能因为其保守就直接删除。

每个 C 元素必须先完成 K 方向点积再参加 Max(N)。如果沿 N 分片，应先合并同一行的分片最大值，再对 M 求和；不能先将每个 N 分片求和后再取最大值。跨核拆 K 则还需要完整的部分点积合并，适合在有明确需求时单独设计。

减少屏障必须伴随数据所有权和依赖的变化。MIX 内 AIC Matmul server、AIV 调用方和空闲参与核的同步契约不能靠删除 SyncAll 来替代。更大的候选空间也需要明确缓冲边界和溢出检查。

## 自动生成用例应覆盖规则的边界

后续用例生成可以根据一套可复现的规则组合：

- 对齐尺寸与相邻尾块；K 仍保持题目要求的 8 倍数。
- 长条、扁平、近方形，以及短 K 和长 K。
- 任务数接近一轮或多轮核数的前后边界，检查空闲核和尾轮。
- 两种 dtype 与四种布局，避免只在一个小 shape 上覆盖转置。
- 随机、全负、零、强抵消和近零输出；保留已有已知答案用例作为锚点。

生成数量、输入字节数和 FP64 golden 工作量都要受控。当前 README 丢失了部分维度/总规模公式，不能声称任意生成组合都是官方合法测试点。

用例身份使用完整输入元数据、数据分布和 seed；计划身份使用实际配置。报告再关联源码/二进制、SDK、硬件和计时口径。人工名称只作显示，不决定算法或匹配结果。测试集合用于发现错误和退化，不能替代未知线上分布；未见过的 shape 仍由同一套规则处理。

## 建议的工程推进顺序

**第一阶段：建立可扩展的规划与验证接口。** 统一问题描述和执行计划，规则生成合法外层分块，加入资源检查和有界启发式选择；runner 导出真实候选；验证器和采样器消费计划；增加规则生成的回归输入。优先复用当前已经存在的执行路径，使第一阶段可以独立检验。

**第二阶段：实现逐块 Matmul 与行最大值融合。** 共同设计 owner 的 B/M 范围、N 遍历或分片、结果块缓冲和必要的跨核合并，减少完整 similarity 的存储生命周期。先取得可验证的融合路径，再扩展布局、尾块和调度变体。

**第三阶段：在合法资源预算内展开流水和专用路径。** 设计双缓冲事件、任务复用和遍历顺序；分别验证固定结构求和与小规模简化路径。低阶 Mmad/LoadData/Fixpipe 实现留作高阶路径确有不足时的选项，避免同时重写所有同步和布局处理。

每阶段交付应包含具体的 kernel 行为变化或可扩展接口、自动正确性覆盖和可复制的线上代码。正常迭代先做正确性回归并看线上反馈；详细性能分析用于解释瓶颈或退化，不再把全量矩阵或仿真设成每一步的前置条件。

全过程保持 `run_kernel` ABI、每次恰好一次 launch，以及只能修改 `kernel.asc`/新增 `.asc`/`.h` 的线上约束。本地工具可以独立演进；开发机无 CANN/NPU 的 CPU 检查不能替代目标 CANN 9.0 的编译、精度和最终得分。


## R13/S9 跨模块审查（2026-10-01）

目标：找出下一轮可能产生结构性收益的模块接口与调度问题，优先保护 S8/S9 已取得的不同收益。只读检查当前源码、README 原题提示、官方 CANN 9.0 文档，并用纯主机规划函数核验结构反例。没有真实输入 metadata、逐点执行计划或新的设备阶段计时；下面的源码事实不能直接对应官方点号。

README 明确提示 Cube/Vector 协同流水、多级存储复用、B/M 并行与尾部均衡、Double Buffer。现框架已经满足单 launch，并缩短了 C 的生命周期，但这些优化尚未形成统一计划。

### 优先级 1：规划器仍按旧执行方式评分

源码证据：`matmul_plan.h:40` 的任务网格为 `B*ceil(M/Tm)*ceil(N/Tn)`，以此计算 waves 和 score。`kernel.asc:426` 先执行 PrepareMatmul，选定外层 tile 与 SDK tiling，随后才调用 MakeStreamPlan。后者实际按 `(batch, M 行块, N 分片)` 调度；流式负载、Vector 消费和最终归约的成本没有反馈给前面的 tile 选择。

此外，`kernel.asc:431` 的 Auto 未命中 Small 时总是 Stream，没有比较 GM 与 Stream 的成本。旧 GM 代码保留不等于在线有自适应选择能力；R13 相当于把旧规划结果交给新调度器执行。

`stream_plan.h:61` 还有一个确定的剪枝盲点：只要行任务数不少于核数，立即返回 S=1。核数用满不等于工作均衡。用现有 MakePlan/MakeStreamPlan/SplitStreamPlan 在主机执行以下合成反例：B=1、M=400、N=1024、K=256、外层 tile=16×64、24 核，得到 25 个行任务，每个含 16 个 N 块。

| 分配方式 | 任务数 | 最忙核的 Matmul 块数 | 显式 scratch 字节 |
| --- | ---: | ---: | ---: |
| R12 GM 网格 | 400 | 17 | 此处不作内存对比 |
| R13 当前 Auto，S=1 | 25 | 32 | 99968 |
| 同 tile，S=2 | 50 | 24 | 103296 |
| 同 tile，S=4 | 100 | 20 | 106624 |
| 同 tile，S=8 | 200 | 18 | 113280 |
| 同 tile，S=16 | 400 | 17 | 126592 |

此表是**真实主机函数的结构输出**，不是 SDK 接受验证或 NPU 测速；也不是猜测官方 shape。S 增大会增加部分 Max、通信与屏障，不能据块数直接选择 S=16，更不能把 32/17 写成提速倍率。它证实的是当前候选剪枝会错过更均衡的合法几何。

下一步应联合生成 `(算法族, Tm, Tn, N 分片, 调度轮次, 缓冲数, 归约方式)`，在 SDK 接受前后保持同一个执行成本描述。先消除任务数/负载描述错位，再比较 Cube 工作、Vector 消费、部分 Max 字节数、屏障和末轮；最终选择来自真实元数据，不能回到官方点号分派。模型尚未校准，先避免有明确结构证据的劣化，不宣称能预测最优耗时。

### 优先级 1：Matmul→Max 有界存储已经融合，跨块流水尚未建立

`stream_matmul.asc:40` 每个 N 块都重新设置形状和 A/B、同步 IterateAll、End，再发起该 C 块的 DMA/Max，等待 MTE2 读完后才提交下一块。最后少量 Vector 指令可能与下一块重叠，但没有显式安排“Cube 算 t+1，同时 Vector 归约 t”的稳定流水。对于一个行块有多个 32 行消费分片的情况，单个 C 槽和单份输入队列会进一步限制提前生产。

与 R12 相比，R13 将 Vector 消费插入每个核的矩乘任务循环；缩小工作集的同时，也可能打断 Cube 连续计算。C 元素仍然有 GM 写读，不能用 scratch 容量减少证明内存流量减少。这是解释 S9 点 8–12 退化的候选之一，尚不能排除任务不均衡、分片合并或其他因素。

建议第一步用双 GM C 槽显式预取下一块：

```text
预热：提交 C0，等待 C0 可读
稳定阶段：提交 C1 异步计算 → 消费 C0 → 等待 C1
          提交 C2 到已读完的槽0 → 消费 C1 → 等待 C2
收尾：消费最后一块，写出完整行 Max
```

此结构只需保持一个 Matmul 计算在途，同时消费上一块，不依赖同一 Matmul 对象支持任意数量的未完成调用。每槽都要区分“可写、计算完成、MTE2 消费完成”；Wait/End 及 shape 变更必须遵守对象生命周期，最后一块必须排空。异步计算完成与旧槽已读完是两条不同依赖，不能删除原 MTE2_S 保护。

官方 [CANN 9.0 异步场景](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_10_10015.html) 和 [WaitIterateAll](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_0641.html) 支持 MIX 中异步提交、需要结果时等待；使用 WaitIterateAll 的示例显式设置了 waitIterateAll 参数。这里只确认接口路线可研究，不表示我们的双槽实现已完成或获得收益。

资源必须跨模块核算：当前归约 UB 峰值为 48544 字节；若仅把 32×256 float 输入队列深度从 1 改到 2，会增加 32768 字节，变成 81312，超过当前 65536 预留。双 GM 槽可以先不翻倍 UB 输入队列；若再做 DMA/Vector 双缓冲，需缩小消费片或重算 Matmul UB 预算，而不是只修改队列深度。

粗略两段模型中，单块串接成本为 `Tc + Tv`，充分重叠后的稳定间隔趋近 `max(Tc,Tv)`，另有预热、排空和同步。只靠两个阶段重叠的理想收益通常不超过该模型下的 2 倍，不能承诺把十几倍差距一次解决；单块输入几乎没有跨块重叠机会。

### 优先级 2：Max→Sum 没有继承上游所有权和并行度

`kernel.asc:121` 按每 8 个 batch 绑定一个最终 Sum owner。活跃求和核数为 `min(已启动核数, ceil(B/8))`：启动 24 核时，B=1/8 仅一个 owner，B=24 也只有 3 个。R12 减少的是核内 Scalar 工作量，M 方向的最终求和仍未跨核分担。

R13 的 producer 在 S=1 时已经拿到整段行的最终 Max，却把每行 Max 写回 GM，再让少量最终 owner 重新搬入和求和。这里可以把**计算所有权**与**最终 32 字节写回所有权**分开：

- S=1：行块 owner 完成全 N 后，在 UB 内生成带补偿的部分和，写出一条独占对齐记录；最终 owner 只按固定顺序合并少量记录。
- S>1：producer 仍写分片行最大值，必须先跨 N 合并逐行 Max；负责这一合并的 owner 再就地做 M 小段的补偿求和，避免完整 maxima 再写读一遍。
- 最后每 8 个 batch 的输出打包仍可由一个核完成。只把少量结果打包串行，不把全 M 的计算一起串行化。

这样减少的是阶段间传输及收尾计算规模：由每 batch 的 M 个行最大值，变为约 `ceil(M/行块大小)` 条部分和记录；必须计入每记录 32B 所有权对齐。它会改变加法分组，应保留高/低部分或等效补偿，固定合并顺序，检查强抵消和近零结果。不能直接换成无序 AtomicAdd；N 分片也绝不能先各自求 Sum 再 Max。

这是 Max 与 Sum 的实质联动，不是再重写一次独立 Sum 指令循环。S9 点 13 几乎没变化并不能证明这一机会无效；也不能保证它一定改善点 13。

### 优先级 2：矩乘任务、输入复用和 Vector 消费粒度绑得过紧

同一行块遍历 N 时 A 不变，但当前每个 N 块都从 GM 设置 A，再结束一次 Matmul 计算。代码没有跨调用保留 A 于 L1 的明确契约；这不证明每次物理上都访问 HBM，SDK/L2 的实际复用未测量。官方 [End](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_0645.html) 的语义是释放矩乘计算资源，不能将反复调用解释成已经建立了 L1 常驻。

后续可把一个 Matmul 计算范围扩展为较长的 N 区间，在库内部完成多个 base tile，再逐块消费。应区分三种粒度：多核负责的工作区间、SDK 内部计算/缓存的块、Vector 一次读入 UB 的片。当前把它们近似绑定在一个外层 Tm/Tn 上，影响通信次数、A 复用、Cube 利用率和 Max 的 UB 占用。

这一方案比双 GM 槽更深入，须核对 iterateOrder、baseM/baseN、尾块和 workspace，不能为了少调用而重新生成巨大的完整 C。官方 [GetTensorC](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_0639.html) 支持按 base tile 消费，并明确提示 UB 太小可能影响 Matmul；异步 VECIN 路线还要检查 NZ 格式约束，接口名不等于物理上消除了 GM 中转。

### 下一轮路线选择与边界

| 路线 | 优先解决的问题 | 代价/局限 | 建议 |
| --- | --- | --- | --- |
| 联合规划与均衡 | 旧 tile 评分和新任务分工错位；过早剪掉 N 分片 | 只有结构成本，不能保证最优；应保留 GM/Stream 对照 | 先修清楚，可独立成一轮 |
| 显式异步双槽 | Cube/Vector 的块间等待 | 生命周期和资源预算变复杂；单块输入受益有限 | 下一轮主要加速候选 |
| Max 完成处就地做部分 Sum | 完整 maxima 写读、最终少核尾部 | 加法分组改变，需要精度验证 | 独立下一轮，避免与流水混改 |
| 长 Matmul 区间 + 分片消费 | 每块库调用与输入复用不足 | 内部 tile/迭代次序/工作空间耦合更深 | 在前两步结果之后推进 |

若以连续版本推进：先使联合规划描述和实际执行一致，再只加入异步双槽，最后独立修改 Max→Sum 的传递格式。每个版本仍收全 15 点，S8 保护点 8–13，S9 保护点 14；点 15 保留为未解决问题。只改变后端或只放宽阈值都不足以完成跨模块优化。

小规模固定开销是另一条边界：只有一两个结果块时流水缺少可重叠工作；纯 Vector 与通用 Matmul server 之间的精简 Cube/Vector 算路仍可能有价值，但不能从最优约 1 μs 就确定任何测试点的真实 shape。主机分配/tiling 缓存可以减少本地 host 时间，当前缺少评测计时证据，不能把它列为线上十倍差距的已知解释。

本次结论来自源码、官方接口和主机结构检查。没有新 kernel、没有 NPU 耗时测量，也不增加本地 NPU 测试前置条件；大幅收益是待验证目标，不能从上述块数或理想模型直接推算线上分数。
