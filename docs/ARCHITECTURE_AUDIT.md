审计日期：2026-09-30；代码参照 `74d810c`。本次检查 README、kernel、runner、测试生成和采样器，不修改执行代码，不产生新的设备性能结论。

当前实现完成了通用正确性 baseline 和一轮有效的并行归约优化，但整体仍采用完整 similarity 中间矩阵和分阶段同步。后续优化应同时考虑分块、任务分工、存储、流水与归约；增加候选数量只是其中一部分。

用户确认的开发方向是规则生成候选、按实际输入自动匹配、自动生成本地用例，以线上结果检验收益。完整性能矩阵和细粒度 profiling 保留作诊断工具，不要求每轮开发都先完成全量采集。

## README 对当前实现的具体提示

题目在[核心难点](../README.md#L36)和[性能要求](../README.md#L116)中明确提出四种布局、非对齐尾块、小 batch、大 M/N/K、Cube/Vector 协作、存储复用、多核均衡及 Double Buffer/Ping-Pong。这些是优化方向，不意味着每项都必须采用某一种实现。

| 模块 | 当前源码事实 | 尚未展开的工程与性能空间 |
| --- | --- | --- |
| 候选生成与选择 | [SelectMatmulPlan](../kernel.asc#L26) 固定四个外层 tile，只按 B/M/N、核数、任务数筛选 | 从输入、对齐、硬件资源生成候选；加入 K、dtype、布局、任务轮数与尾块成本；限制规划开销 |
| Matmul 内部 tiling | [RunKernel](../kernel.asc#L340) 使用 CANN MatmulApiTiling，内部基本块交给库决定，UB 预算固定为 128 KiB | 明确外层任务与内部 baseM/baseN/baseK 的区别；结合归约缓冲、队列深度和通信空间核算资源 |
| 多核调度 | [GetMatmulBlock](../kernel.asc#L64) 和 [任务循环](../kernel.asc#L212) 将 B/M/N 网格按核编号跨步分配 | 按输入选择行块所有权、N 分片、任务遍历顺序；考虑尾轮再分配、A/B 复用和归约负载 |
| 中间存储 | [scratch 分配](../kernel.asc#L331) 为全部 FP32 similarity 和行最大值留空间 | 在结果块产生后尽早归约，缩短 similarity 生命周期；根据分片方式设计有界中间空间 |
| Cube 与 Vector 协作 | [MatmulMaxSum](../kernel.asc#L191) 完成全部 Matmul 后同步，再处理全部行最大值，再同步求和 | 将结果块的生产、消费和完成通知组织成流水；同步范围跟随数据所有权设计 |
| 双缓冲 | [ComputeRowMaxima](../kernel.asc#L80) 的显式队列深度为 1，没有在我们的代码层设计下一块搬运与当前块归约的重叠 | 设计预取、计算、写回的缓冲生命周期与事件依赖；不能仅将队列深度改成 2。Matmul 库内部是否双缓冲需另查其实际配置 |
| 两级归约 | 行最大值已批量并行；[SumRowMaxima](../kernel.asc#L137) 仍按行执行 FP32 补偿求和，每组输出有唯一 owner | 研究固定结构的向量/树形求和及必要的补偿；平衡数值误差、可重复性和串行尾部开销 |
| 不同规模与布局 | dtype、TA/TB 已模板化，但所有输入仍走同一种总体数据流 | 根据计算规模和布局准备少量有实质差别的 kernel 路径；小规模路径减少准备、通信和同步，大规模路径侧重复用与流水 |
| Host 调用 | 每次创建 tiler、分配 scratch/workspace、等待完成并释放 | 将规划成本与设备成本分开考察；不能为了消除同步而破坏临时内存生命周期，也不能从未知线上计时口径推断分配占比 |
| 验证与采样 | [performance_cases](../scripts/perf_local.py#L28) 是人工选择数列的单轴扫描；[tile_sweep](../scripts/tile_sweep.py#L10) 固定五个策略名称 | 规则生成组合与边界用例，按输入身份和计划身份自动匹配，避免工具层重复硬编码 kernel 的候选列表 |

这些缺口由源码可以确认。它们各自占多少耗时、在哪些输入下有收益，仍是待验证问题，不能从一个流水占比或线上点号推断。

## 核心数据流仍有三段阶段边界

当前单次 kernel 内的顺序是：

```text
所有 Matmul 任务 → 完整 similarity 写 GM
    → 全 AIV 同步
    → 所有行最大值任务 → maxima 写 GM
    → 全 AIV 同步
    → 每个输出 owner 串行补偿求和
```

当前显式 scratch 字节数为：

```text
4 * B * M * round_up(N, 16)
  + 4 * B * round_up(M, 32)
```

此外还有 Matmul 系统 workspace。一次 kernel launch 满足了平台启动次数要求，但不代表已经实现了逐块数据复用和跨阶段流水。

官方 [Matmul + Abs 直调示例](../cann-learning-hub/tutorials/ascendc_operator_development_light/03_simple_operator_practice/answer/03.05/matmul_abs.asc) 提供了 Iterate/GetTensorC 后接 Vector 处理的流程，可以作为候选数据流的参考。示例为固定 shape、FP16、有 bias、MIX 1:2，不能直接替换我们的 BF16/四布局/尾块处理。910B 上 LocalTensor 接口也不保证底层完全绕过 GM。

## 分块规则目前在四处重复

1. `kernel.asc` 的候选数组和 policy 编号范围。
2. [local/runner.asc](../local/runner.asc#L45) 的字符串到编号映射。
3. [scripts/local_baseline.py](../scripts/local_baseline.py#L174) 的候选白名单与计划校验。
4. [scripts/tile_sweep.py](../scripts/tile_sweep.py#L10) 的遍历列表和表头。

因此，当前增加一种 tile 需要同步修改选择、控制、验证和报告四层。校验应继续严格，但应检查实际执行计划的结构、约束和身份，而不是让 Python 复制一份独立的候选生成算法。

值得采用的边界是：Host 规划器产生完整的执行计划；本地 runner 能导出同一规划器产生的候选及最终选择；采样器按候选清单运行并记录实际执行计划。Device 只执行已选择的合法方案。正式调用中不进行试跑搜参，候选枚举也要有数量和 Host 开销上限。

## 各优化模块必须共同决定的事情

分块不是孤立的两个整数。一个执行方案还包含任务所有权、内部 Matmul 配置、缓冲数量、结果块格式、N 分片数、归约方式和同步参与者。

例如，增大 C 块可能减少 Matmul 调用，却挤占 UB，使双缓冲或行最大值暂存无法成立；只沿 M 分工有利于在 owner 内累计行最大值，但小 B/M、大 N 时可能任务不足。候选合法性和选择必须考虑这些耦合。

可以按三层组织后续设计：

- **问题与硬件描述**：逻辑 B/M/N/K、真实存储跨度、dtype、布局、可用核数和目标资源能力。保留现有 metadata 校验，避免重复解释 transpose。
- **计划生成与约束检查**：由规则产生分块和调度候选，排除资源不合法的组合，再用有明确假设的成本估计选择方案。外层 tile 与库内部 tiling 分别记录。
- **设备执行与验证**：少量明确的 kernel 路径消费计划；本地工具导出候选、生成输入、验证结果并关联测量。后续决策树是选择规则的一种表达方式，不要求每个分支对应一个手写 shape。

这些是架构讨论的边界，具体数据结构、文件拆分和 API 需在实现设计中确定；模块化本身不等于性能提升。

## 数值正确性与调度空间

README 要求先沿 N 取最大值，再沿 M 求和，并要求重复结果一致。它没有规定 M 维求和必须采用当前逐项串行 Kahan 顺序。

因此，固定结构的树形或向量求和可以作为候选，但 FP32 加法重排会改变误差，必须通过 FP64 golden、强抵消、近零结果和重复一致性检查。现有串行补偿求和是可用的参照，不能因为其保守就直接删除。

每个 C 元素必须先完成 K 方向点积再参加 Max(N)。如果沿 N 分片，应先合并同一行的分片最大值，再对 M 求和；不能先将每个 N 分片求和后再取最大值。跨核拆 K 则还需要完整的部分点积合并，适合在有明确需求时单独设计。

减少屏障必须伴随数据所有权和依赖的变化。MIX 内 AIC Matmul server、AIV 调用方和空闲参与核的同步契约不能靠删除 SyncAll 来替代。更大的候选空间也需要明确缓冲边界和溢出检查。

## 自动生成用例应覆盖规则的边界

后续用例生成可以根据一套可复现的规则组合：

- 对齐尺寸与相邻尾块；K 仍保持题目要求的 8 倍数。
- 长条、扁平、近方形，以及短 K 和长 K。
- 任务数接近一轮或多轮核数的前后边界，检查空闲核和尾轮。
- 两种 dtype 与四种布局，避免只在一个小 shape 上覆盖转置。
- 随机、全负、零、强抵消和近零输出；保留已有已知答案用例作为锚点。

生成数量、输入字节数和 FP64 golden 工作量都要受控。当前 README 丢失了部分维度/总规模公式，不能声称任意生成组合都是官方合法测试点。

用例身份使用完整输入元数据、数据分布和 seed；计划身份使用实际配置。报告再关联源码/二进制、SDK、硬件和计时口径。人工名称只作显示，不决定算法或匹配结果。测试集合用于发现错误和退化，不能替代未知线上分布；未见过的 shape 仍由同一套规则处理。

## 建议的工程推进顺序

**第一阶段：建立可扩展的规划与验证接口。** 统一问题描述和执行计划，规则生成合法外层分块，加入资源检查和有界启发式选择；runner 导出真实候选；验证器和采样器消费计划；增加规则生成的回归输入。优先复用当前已经存在的执行路径，使第一阶段可以独立检验。

**第二阶段：实现逐块 Matmul 与行最大值融合。** 共同设计 owner 的 B/M 范围、N 遍历或分片、结果块缓冲和必要的跨核合并，减少完整 similarity 的存储生命周期。先取得可验证的融合路径，再扩展布局、尾块和调度变体。

**第三阶段：在合法资源预算内展开流水和专用路径。** 设计双缓冲事件、任务复用和遍历顺序；分别验证固定结构求和与小规模简化路径。低阶 Mmad/LoadData/Fixpipe 实现留作高阶路径确有不足时的选项，避免同时重写所有同步和布局处理。

每阶段交付应包含具体的 kernel 行为变化或可扩展接口、自动正确性覆盖和可复制的线上代码。正常迭代先做正确性回归并看线上反馈；详细性能分析用于解释瓶颈或退化，不再把全量矩阵或仿真设成每一步的前置条件。

全过程保持 `run_kernel` ABI、每次恰好一次 launch，以及只能修改 `kernel.asc`/新增 `.asc`/`.h` 的线上约束。本地工具可以独立演进；开发机无 CANN/NPU 的 CPU 检查不能替代目标 CANN 9.0 的编译、精度和最终得分。
